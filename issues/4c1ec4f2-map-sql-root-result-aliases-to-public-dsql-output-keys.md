# Map SQL root result aliases to public DSQL output keys

**ID:** 4c1ec4f2 | **Status:** Done | **Created:** 2026-06-11T18:35:53+02:00

## Summary

Generated runtime output should expose public DSQL output keys, not internal SQL
root result aliases.

## Context

`crates/core/src/sql/postgres.rs` uses `SelectionContext.result_alias` for the
root select alias. That alias is a hashed internal identifier generated by
`context_for(...)` to keep PostgreSQL identifiers short and collision-free.

Generated TypeScript metadata exposes `plan.output_name` as the public result
field. If the executor returns `rows[0]` unchanged, callers can receive an
object keyed by an internal alias such as `movie_info_result_d37aaa02` while
the generated TypeScript result expects a stable public key such as
`movie_info`.

Internal SQL aliases and public output aliases should remain separate concepts:

- Internal aliases are compiler-owned implementation details and can be hashed,
  shortened, and collision-proofed for PostgreSQL.
- Public output aliases are user-authored API shape and must round-trip into
  JSON keys, TypeScript result types, source maps, and executor output.

## Done When

- Runtime-facing metadata or generated code maps root SQL result columns back to
  public DSQL output keys, or root SQL aliases are safely made public with a
  precise validation strategy.
- Generated TypeScript result keys match executor output keys.
- Nested internal aliases continue to be hidden behind public JSON object keys.
- Tests cover a default root field and a user-authored root alias.
